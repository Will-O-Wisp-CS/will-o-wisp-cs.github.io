# 公認CSサポート 自動申請 設計書

- 作成日: 2026-11-17
- 状態: 承認済み

## Context
鬼火CSは dmp-ranking.com の店舗管理画面から「公認CSサポート○月開催申請」を出して開催している。
これまでは開催ごとに Google スプレッドシート（申請項目を1行ずつ並べたもの）をコピーして書き換え、それを見ながら手で入力していた。
申請に使う店舗アカウントは3つ（A・B・C）。1アカウントにつき1か月2回まで開催できるので、月に最大6枠。どのアカウントでどの会場を出すかに決まりはない。

**目的:** 主催者が「どの枠で・どの会場で・何日に」を選ぶだけで、入力から申請完了までを自動で行う。

## ゴール / ゴールでないもの
- ゴール
  - GitHub Actions の Run workflow 画面で、6枠（A①〜C②）ごとに会場と日付を指定して実行すると、その枠の開催を申請まで済ませる
  - 全部空欄で実行すると、指定月の6枠の状態を一覧で出す
  - 「確認だけ」で、入力まで済ませて保存しない試し運転ができる
- ゴールでないもの
  - リモートデュエマ・ファンイベント・全国大会店舗予選の申請
  - 申請済みの開催の内容変更・中止申請・結果報告
  - 会場のひな形を画面から編集すること（JSON を手で直す）
  - スガツールのイベント作成（別スクリプト）
- 失敗とみなすこと
  - 指定していない枠や、申請済みの開催を書き換える
  - 一部だけ入力された状態で申請してしまう
  - ログイン情報がログ・スクリーンショット・リポジトリに出る

## 方式の検討（Approaches）
1. **GitHub Actions + Playwright（採用）** — Run workflow 画面から実行。ログイン情報は Secrets。スマホからも使える。実行に1〜2分かかり、確認はログとスクリーンショットになる
2. PC で動かすコマンド — PC がないと申請できないので不採用
3. サイトに申請ページ（`/apply/`）を作り、裏で Actions を動かす — 空き状況を画面に出せるが、GitHub トークンをブラウザに入れる必要があり、枠の状態を公開リポジトリに載せる問題もある。作る量が2〜3倍になるので不採用
- 申請画面は textarea の中身を JavaScript で hidden 項目に写してから送るなど、画面側の処理に頼っている。そのため HTTP を自前で組み立てず、Playwright でブラウザを操作する（主催者の判断ではなく設計上の判断）

## 使い方
`.github/workflows/apply.yml`（名前「大会を申請」、`workflow_dispatch` のみ）。入力は次の14個。

| 入力 | 種類 | 内容 |
|---|---|---|
| `month` | string（必須） | 申請する開催月 `2027-01`。全角・`2027/1` も受け付ける |
| `a1_venue` 〜 `c2_venue` | choice | 空欄＋ひな形のある会場名 |
| `a1_date` 〜 `c2_date` | string | 開催日。`10` / `1/10` / `2027-01-10` のどれでもよい |
| `dry_run` | boolean（既定 true） | 確認だけ。外すと本当に申請する |

- 会場と日付の片方だけ埋まっている枠はエラーにして、どの枠も申請しない（入力ミスとみなす）
- 日付が `month` の月でなければエラー
- 開始時刻・定員は会場のひな形の値を使う（開催ごとの上書き欄は付けない。入力が25個の上限に近づくため）
- 同時に2本走らないよう `concurrency: apply` を付ける

## ログイン情報（Secrets。主催者が自分で登録する）
- `DMP_A_ID` / `DMP_A_PASSWORD`、`DMP_B_…`、`DMP_C_…`
- `DMP_CONTACT_MAIL` — 担当者メールアドレス（公開リポジトリに置かないため）
- 必要な Secrets がないアカウントの枠を指定したら、そのアカウントだけエラーにする
- パスワードはログに出さない（Actions のマスクに加え、コード側でも出力しない）

## 店舗管理画面（2026-11-17 に画面から読み取ったもの）
すべて `https://www.dmp-ranking.com/`、Shift_JIS。サイトの更新で変わりうる。

- ログイン: `shop/` の `form1`（`LoginID` / `Password`、ボタン「ログイン」→ `SubmitCheck()` → `POST /shop/index_bin.asp`）→ `shopindex.asp`（管理モード選択）→ 「DMPランキング管理」（`shopmenu.asp`）
- `shopmenu.asp`: 申請の一覧表。行は「大会名 / 実施可能期間 / 申請受付期間 / 状態 / リンク」
  - 対象行は大会名がちょうど `公認CSサポートYYYY年M月開催申請`（【リモートデュエマ】などの付いた行は対象外）
  - 未申請の月は「申請する」ボタン（`location.href='shopevent.asp?EventID=356'`）。申請後は状態（「申請確認中です」「承認されました」「差し戻されました」など）と「大会詳細・結果報告」リンク
  - 申請受付期間の外の月はボタンがない（「申請受付終了」）
- `shopevent.asp?EventID=…`: 月の申請画面。「実施上限：2回」。開催ごとのブロックに実施日・状態・参加表明・締切の変更欄
  - ブロックの表示順と `Seq` は一致しない（12月分では1回目のブロックが `Seq=2`）。枠は Seq ではなく「登録済みの開催の数」で数える
  - 開催の追加・編集は `shopeventsub.asp?EventID=…&Seq=…`
  - 〔上記内容で申請する〕（`SubmitCheck()`、`confirm` あり）→ `POST /shopevent_bin.asp`。**〔更新保存〕だけでは申請されない**（管理メニューの注意書き）
- `shopeventsub.asp`: 開催の詳細。`form1`（`multipart/form-data`、`POST /shopeventsub_bin.asp`、〔更新保存〕→ `SubmitCheck()`）

## 会場のひな形（`src/apply/venues.json`）
```json
{
  "common": { "entryFee": 1500, "details": "■マッチングサイトについて…", "bringing": "・デッキ…", "organizer": "鬼火CS運営", "judges": [6012] },
  "venues": [
    {
      "name": "竜星の嵐新宿店", "reception": "10:10", "start": "10:30", "capacity": 80,
      "pref": 13, "address": "新宿区西新宿1-18-1小川ビル 5F", "tel": "03-6276-6167",
      "coordinate": 1, "lat": "…", "lng": "…", "mapUrl": "",
      "schedule": "10:10～10:30：大会受付…", "prize": "1位\n・商品券10,000円分…",
      "formatBiko": "■予選…"
    }
  ]
}
```
- 会場は **竜星の嵐新宿店** と **晴れる屋3** の2つ。中身は主催者が共有したスプレッドシート（各1枚）から作る
- 大会フォーマット（`formatBiko`）は会場で違う（晴れる屋3は最大6回戦・上位14名、竜星の嵐新宿店は5回戦・上位16名）ので会場ごとに持つ
- `lat` / `lng` / `coordinate` / `mapUrl` は各会場の承認済みの開催の詳細画面から写す（晴れる屋3: 35.7135625 / 139.7034415、座標は会場住所）
- `apply.yml` の会場の選択肢は `venues.json` の会場名と同じにする（ずれたら落ちるテストを置く）
- 共通の文面（大会詳細など）は今回のシートの内容を初期値にする

## 処理の流れ（`src/apply/apply.ts`、Node 専用）
1. 入力を検証（純粋関数）。誤りがあればログインせずに exit 1
2. 枠を指定したアカウントごとに（全部空欄なら3アカウントとも）ログイン → `shopmenu.asp` で対象月の行を探す
   - 行がない・申請受付期間外なら、そのアカウントの枠はすべて「申請できない」として飛ばす
3. 月の申請画面を開き、登録済みの開催（実施日・状態）を読む。空き枠の数 = 2 − 登録済みの数
   - 指定した枠の数が空き枠より多ければ、そのアカウントの指定はすべて飛ばして理由を出す（どれを優先するか勝手に決めない）
   - 同じ日付の開催が登録済みなら飛ばす（二重申請の防止）
4. 空き枠ごとに詳細画面を開いて入力。`dry_run` ならここでスクリーンショットを撮って保存せずに終わる
5. 〔更新保存〕→ 月の申請画面に戻り、登録済みの開催に入っていることを確認 → 〔上記内容で申請する〕（`confirm` は承認）
6. 管理メニューで状態が「申請確認中です」になったことを確認
7. 最後に6枠の状態（空き / 申請確認中 / 承認 / 差し戻し / 今回申請 / 飛ばした理由）を表にして、ログと `$GITHUB_STEP_SUMMARY` に出す。1つでも失敗があれば exit 1（GitHub からメールが届く）

- 枠のラベル（①②）はアカウント内の順番にすぎない。状態一覧は登録済みの開催を日付順に①②と表示する
- スクリーンショット（入力後・申請後）は `actions/upload-artifact` で保存期間 7日。ログイン画面は撮らない

## 構成
```
.github/workflows/apply.yml
src/apply/
  apply.ts        Node 専用の入口（Playwright でブラウザを操作）
  input.ts        Run workflow の入力 → 申請する枠の一覧（検証）
  fields.ts       会場のひな形 + 日付 → 詳細画面に入れる値（日時の計算を含む）
  menu.ts         管理メニュー・月の申請画面の HTML → 対象月の行・登録済みの開催
  summary.ts      6枠の状態表（Markdown）
  venues.json
  *.test.ts
```
- 機能フォルダだが画面はない（`index.html` を作らず、メニュー・トップにも載せない）
- `apply.ts` から import するファイルは `.ts` 拡張子付きで書く（`fetch.ts` と同じ）
- `package.json` に `"apply": "node src/apply/apply.ts"` と devDependency `playwright`。Actions では `npx playwright install --with-deps chromium`
- 純粋関数（`input` / `fields` / `menu` / `summary`）は vitest でテストする。`menu.ts` のテストには今回読み取った画面の HTML を縮めたものを使う

## 実装側で決めたこと（主催者が確認する）
- **公開リポジトリでの見え方:** Actions のログ・状態表・artifact と `venues.json` は第三者も見られる。主催者は公開のままでよいと確認済み（非公開リポジトリに分けない）
  - スクリーンショットは担当者メールアドレス欄を Playwright の `mask` で隠して撮り、artifact の保存期間は1日にする
  - 状態表に出すのは開催日・会場・状態だけにする（承認後は大会ページで公開される情報）
- **途中で失敗したとき:** アカウント内で指定した枠をすべて〔更新保存〕できたときだけ〔上記内容で申請する〕を押す。1件でも失敗したら、そのアカウントは申請せず、保存済みの開催はそのまま残して状態表に「保存のみ（未申請）」と出す
  - 次の実行で、未申請の保存済み開催がある月を見つけたら、そのアカウントは何もせずに止める（人が画面で確かめる）
- **差し戻された開催:** 登録済みとして2回の上限に数える。直して出し直すのは範囲外
- **進め方:** ①純粋関数とテスト → ②`dry_run` だけ動く版で、未申請の月の画面を確かめる → ③主催者が見届けて本番の申請を1件行い、申請後の画面に合わせて手順5・6を仕上げる

- **2つ目の開催の追加:** 1つ目が承認済みの月に2つ目を足すと1つ目の承認はいったん取り消されるが、両方あらためて承認されるので構わない（主催者確認済み）。ツールは承認済みの月にも足して申請する

## 未確定・実装時に確かめること
- 未申請の月の画面（2026-11-17 に確認）: 空き枠の「○回目開催情報」は `EventAdd('')`、状態は「開催されません」。新しい開催は `shopeventsub.asp?EventID=…&Seq=`（Seq 空）で開き、サーバーが Seq を振る（`Mode=Add`）
- 新しい開催の詳細画面の `Lat` / `Lng` の初期値はアカウントの店舗の座標なので、ひな形の座標を必ず入れる
- 申請受付期間内かは、管理メニューの行の「申請受付期間」と JST の今日で判定する（承認済みの月は期間外でもリンクがある）
- 1つ目を登録済みの月に2つ目を足すときも `Seq=` 空でよいか、〔上記内容で申請する〕のあとの画面は、本番の1件目で確かめる
